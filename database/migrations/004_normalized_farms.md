# Normalized farm migration

FarmDetails contains one row per farm, owned by users through user_id. farm_crops contains an unlimited number of season records per farm. All currently captured fields have explicit columns; measurements and dates use native SQL types. Previous crop fields map to the same crop columns as current fields, with additional yield, treatment and residue columns.

Stop application writes during migration. Build the server with `npm --prefix server run build`, then run `node server/scripts/migrate-normalized-farms.mjs` from the repository root with the existing database environment configured. The script creates tables, backfills all nonempty legacy profiles (including inactive users), verifies every populated field and only then drops users.farm_details. A conflicting existing record aborts before dropping the column. Restart with the updated server and clients. Do not run the historical 002 migration afterward.

PATCH /api/auth/me accepts farmDetails plus optional farmId (UUID or "new") and newCrop (boolean). Omitted farmId retains compatibility by targeting the first farm. newCrop archives the current record and creates a new one, even for the same crop name in a different year. Ordinary saves update the current record. addPreviousCrop appends an independent previous crop from the previous fields, requires at least one nonempty detail and leaves the current crop unchanged. The web and mobile interfaces show this optional history separately, with Add previous crop / Add more previous crops actions. The previous-crop form edits the latest historical crop; older seasons are retained and returned in farms[].crops. Starting a new crop ignores legacy previous fields to preserve the archived current record. Farm ownership is checked in the same transaction as writes; user-row locking serializes seasonal transitions.

The response includes farms[] with details and crops[], and the legacy farmDetails property projects the first farm for older consumers.
